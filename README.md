# hermes-github-mentions

Mention your bot on GitHub to give your self-hosted [Hermes Agent](https://github.com/NousResearch/hermes-agent) a task.
The watcher checks the bot account's notifications, verifies the request's author,
and forwards it to a local Hermes webhook. Hermes does the work and is instructed
to reply in the original GitHub thread. Discord notifications are optional.

You don't need repository admin access or a public webhook endpoint. The bot
does need access to the repository and must receive GitHub mention notifications.

This is a native Hermes plugin with an optional standalone CLI. It includes
request recovery, duplicate detection, issue and PR comments, inline reviews,
and Discussions with paginated comments and replies. The watcher uses Python's
standard library. In plugin mode, Hermes starts and stops its background worker
with the gateway through the registered `github_mentions` adapter.

## How it works

```text
GitHub @mention
    -> bot account notifications
    -> author approval check
    -> saved request + signed local webhook
    -> Hermes agent
    -> reply in the original GitHub thread
```

The watcher makes read requests to GitHub. GitHub writes are performed by Hermes,
under the tools and permissions you configure there. Its GitHub credentials must
belong to the same bot account. No Hermes source patches are required for the
routes generated by this project.

## Requirements

- Python 3.11 or newer on Linux or macOS. The single-writer lock uses `fcntl`.
- A running Hermes gateway with webhooks and the toolsets in
  the generated routes. The route format was checked against a local Hermes
  checkout on October 27, 2026. See the [webhook reference](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/webhooks).
- A GitHub bot account and a token that can read that account's notifications
  and the relevant repositories. The watcher verifies the token's login at startup.
- GitHub CLI access for the Hermes agent as that bot, with permissions for the
  requested work. A successful webhook handoff does not prove those permissions.

GitHub.com is supported. GitHub Enterprise and GitHub App installation tokens are
not supported. Notification polling needs a user identity.

## Install as a Hermes plugin

Install from GitHub and enable the plugin:

```bash
hermes plugins install luantak/hermes-github-mentions --enable
```

This plugin does not install Python dependencies or modify Hermes source files.
It uses Hermes' default `in_process` plugin mode. Hermes' separate plugin-host
isolation mode cannot run gateway adapters.

Save the bot and requester accounts in Hermes settings:

```bash
hermes github-mentions configure \
  --bot example-bot \
  --author example-owner
```

Repeat `--author` to approve more users. Approved users can request work in any
repository the bot can access and receive mention notifications from. Settings live under
`plugins.entries.hermes-github-mentions.settings` in the active profile's config.
The manifest's `config_schema` also exposes them in Hermes Desktop's plugin
settings form.

Requests and replies stay on GitHub. When the active Hermes profile has Discord
connected and a destination configured, it also receives copies of replies and
status notices. No Discord account, bot, or channel is required. If Discord is
unavailable, the agent's local response is recorded in Hermes' logs. If it cannot
finish or verify a task, it is instructed to explain that limitation on GitHub.

Discord uses Hermes' configured home channel by default. `/github-mentions set`
chooses the current Discord channel or thread; `/github-mentions status` shows
the selection, and `/github-mentions reset` restores the home-channel default.
Only users explicitly listed in the active profile's Discord allowed users can
change the destination.

From the CLI, `configure --no-discord` turns off Discord notifications, while
`configure --discord` restores automatic use when available. The optional
`--discord-chat-id CHANNEL_ID` flag enables notifications in a specific channel.
Omitted Discord options keep the current settings when reconfiguring.
Changes apply to new requests and status notices. Responses to requests already
running keep the destination selected when the request started. Optional notice
delivery failures are logged without blocking GitHub task processing.

Set these secrets in the active profile through Hermes Desktop's secret fields,
`hermes config`, or your existing profile secret-management procedure:

| Secret | Value |
|---|---|
| `GITHUB_MENTIONS_TOKEN` | Bot user token with notification and repository access. |
| `GITHUB_MENTIONS_WEBHOOK_SECRET` | Shared ASCII webhook secret of at least 32 characters. |

Use a random webhook secret. For example, `python3 -c 'import secrets;
print(secrets.token_hex(32))'` generates one locally. The plugin reads credentials
through Hermes' profile-scoped secret API. It does not parse `.env`, use the
standalone token file, or fall back to another profile's credentials.

Export the webhook routes and adapter enablement block:

```bash
hermes github-mentions routes --output /path/to/private/hermes-routes.json
```

The output contains the webhook secret and is created with mode `0600`.
Merge its `platforms` settings into your Hermes `config.yaml`, preserving existing
platforms and webhook routes. The output enables `platforms.github_mentions`
and defines the local work routes and optional Discord routes. The watcher only
uses the Discord routes when notifications are enabled. Review the
work routes' explicit toolset grants before restarting the gateway.
The export command does not change gateway configuration itself.

Check access with `hermes github-mentions run --dry-run`, then restart the gateway
using your normal procedure. Hermes will create the adapter and start polling.
You do not need the standalone systemd service in plugin mode.

```bash
hermes github-mentions status
```

`status` reads the saved cursor and queue counts. The gateway's platform status
reports connection health. Native watcher state lives at
`<active Hermes home>/plugin-data/hermes-github-mentions/state.json`, outside the
plugin installation tree, so plugin updates do not remove it. A second worker
using that state file is refused.

`hermes github-mentions run --once` and `run --dry-run` are useful for foreground
checks. A real foreground poll shares the native state lock and cannot run
alongside the enabled gateway adapter. Dry runs are read-only.

For a multiplexed profile, run configuration in that profile's Hermes context,
set `--profile NAME`, and set `--webhook-url http://127.0.0.1:8644/p/NAME/webhooks`.
Both the settings and worker credentials remain bound to the active profile.

## Standalone CLI

No dependency installation is needed. Run these commands from the project directory.

1. Create a config and a random webhook secret. Replace the example accounts.

   ```bash
   python3 -m hermes_github_mentions init --bot example-bot --author example-owner
   ```

   The default config is `~/.config/hermes-github-mentions/config.toml`.
   Set `--config /path/config.toml` before the subcommand to use a different location.
   Repeat `--author` to allow more than one requester.

2. Edit the config to set the approved GitHub authors. Their mentions are accepted
   across repositories. Paths resolve relative to the config file.

   Supply the bot token through the configured environment variable, or set
   `token_file` to a private file containing only the token. Keep credential files
   outside the checkout and readable only by your account. The watcher does not
   import tokens from your live Hermes `.env` file.

3. Generate a private Hermes config fragment. The default routes run tasks and
   keep replies on GitHub, with the agent's local response written to Hermes' logs.

   ```bash
   python3 -m hermes_github_mentions routes \
     --output "$HOME/.config/hermes-github-mentions/hermes-routes.json"
   ```

   This JSON file contains the shared webhook secret. JSON is also valid YAML.
   Merge its `platforms.webhook` settings into your Hermes `config.yaml`, preserving
   existing routes and platform settings. The command never edits Hermes files.
   Match the generated host and port to your gateway if you changed `webhook_url`.
   Reload Hermes using your normal procedure after reviewing the configuration.

   The work routes explicitly grant `terminal`, `file`, `web`, `skills`, and `todo`.
   Review those grants for your agent environment. To add optional Discord
   notifications, set `discord_notifications = true` in the watcher config before
   generating routes. Delivery then uses Hermes' Discord home channel, with
   `--discord-chat-id` available as an override. Notice routes use `deliver_only`,
   so notices do not start another agent run.

4. Check notification access without starting agent work.

   ```bash
   python3 -m hermes_github_mentions run --dry-run
   ```

   This makes GitHub read queries, including GraphQL queries for Discussions.
   It does not POST to Hermes, write state, or acquire a state lock. A new config
   starts at the current time, so old mentions normally won't appear. Mention
   the bot after starting the continuous watcher for the first real test.

5. Run the watcher, then create a new GitHub comment such as
   `@example-bot please investigate the failing test` from an allowed account.

   ```bash
   python3 -m hermes_github_mentions run
   ```

   `run --once` performs one real poll. `status` shows the local cursor and queue
   counts without loading credentials. Polling waits at least 60 seconds and
   honors GitHub's longer poll intervals and rate-limit retry headers.

## Standalone service

Linux users can adapt [the systemd user service](examples/hermes-github-mentions.service).
Set its checkout path and Python executable first. Configure `token_file`, or use
the optional private `credentials.env` file with the configured token variable.

```bash
mkdir -p "$HOME/.config/systemd/user"
cp examples/hermes-github-mentions.service "$HOME/.config/systemd/user/"
systemctl --user daemon-reload
systemctl --user enable --now hermes-github-mentions.service
journalctl --user -u hermes-github-mentions.service -n 50
```

Use a single watcher per state file. The lock rejects a second writer.

## Recovery and limits

- A fresh state file starts now. Existing state resumes from its saved cursor,
  with a five-minute overlap. Don't delete the state file to fix a delivery error.
- Requests are saved before delivery. The cursor advances only after a successful
  poll. Requests held during a gateway restart survive a watcher restart.
- Stable webhook delivery IDs and saved hashes suppress duplicates. An edited
  mention is a new request. This is retryable delivery, not an exactly-once
  guarantee. Recovery also depends on Hermes' own delivery deduplication.
- Detection depends on GitHub notifications whose current reason is `mention`.
  It does not search every comment or reconstruct all historical mentions.
- REST scans are capped at ten pages per endpoint. Discussion connections are
  capped at 100 pages each. Exceeding a cap keeps the cursor for retry and requires
  investigation rather than silently skipping data.
- English and German notice text use a simple language heuristic. The agent is
  instructed to follow the original request's language. Other languages use
  English notices.
- The example route asks the agent to verify work and publish one concise reply.
  Those are agent instructions, not an enforced publishing approval gate.
- Localhost delivery, HMAC signatures, and author checks do
  not make repository contents trustworthy. Keep the agent's execution
  environment and permissions appropriate for the repositories it reads.

## Optional progress tracking

For additional Discord progress notices, enable Discord notifications, set
`progress = true`, point `hermes_home` at the relevant Hermes home, and
regenerate the routes to include the direct progress route. For a multiplexed
profile, also set `profile` and use its `/p/PROFILE/webhooks` URL as documented by
Hermes. No progress route or database access is used by default.

Progress tracking reads Hermes' internal `sessions` and `messages` SQLite tables
in read-only mode. It tracks webhook sessions, stops reporting completed turns,
and limits waiting and stale notices. This depends on
Hermes internals and can break after an upgrade. Progress errors do not stop
notification polling. Disable it if your Hermes version uses a different schema.

## Development

```bash
mkdir -p .test-tmp
TMPDIR="$PWD/.test-tmp" PYTHONDONTWRITEBYTECODE=1 \
  python3 -m unittest discover -s tests -v
```

Tests use temporary files and SQLite databases, fake GitHub responses, and fake
webhook responses. Unmocked network requests fail. There are no external test
dependencies. No live Hermes instance or GitHub credentials are needed.

Optional integration tests can use an existing Hermes installation for admission,
Plugin Doctor, real plugin discovery, settings, and adapter startup/shutdown.
Set `HERMES_TEST_ROOT` and put that source root on `PYTHONPATH`, then use its
existing Python environment. For this check, `TMPDIR` must be a disk-backed
directory outside the checkout because Plugin Doctor copies the plugin into
that directory. These tests use an isolated Hermes home and fake credentials;
they do not connect to GitHub or a running gateway.

```bash
HERMES_TEST_ROOT=/path/to/hermes-agent \
PYTHONPATH=/path/to/hermes-agent TMPDIR=/path/to/disk-scratch \
  /path/to/existing/hermes-python -m unittest discover -s tests -v
```

See [native plugin configuration](examples/hermes-plugin.example.yaml) for the
settings layout. Changes to Hermes' built-in GitHub
comment adapter and Discord adapter are separate upstream work and are not
bundled here. See [the release checklist](docs/release-checklist.md) for validation
and compatibility checks.
